# 协作规则与阶段检查

## 1. 文件与职责边界

本包的产出路径是相对 **确认后的目标代码库** 的建议逻辑路径，不证明仓库中已有这些文件。`source/`、本包 `prompts/` 和本包说明文件则相对本包目录。S01 必须先按真实目录写 `docs/engineering/ownership.md`；不要为符合本包虚构目录而重构已有架构。

| 区域 | 唯一维护者 | 其他人如何参与 |
|---|---|---|
| 编辑器组件、Three.js、上游状态适配、页面样式、前端构建配置 | A | C 提内容，D 提问题，B 给契约 |
| API、数据库、授权、后台任务、服务端模型调用 | B | A 提接口需求，D 报告失败 |
| 共享 schema、API 类型、校验、模拟响应、物料汇总纯函数 | B | A 评审适配，C 交 fixture，任何改动有版本说明 |
| `fixtures/product/`、`docs/product/`、素材清单 | C | A/B 提格式约束，D 引用事实 |
| `qa/`、`pitch/`、`evidence/`、测试环境与演示说明 | D | A/B 提运行证据和修复，C 核查产品表述 |
| 运行部署说明、费用实际记录、集成分支与依赖锁文件 | B | A 可提出前端依赖变更；D 汇总，不共同改同一行 |
| 本包 `TASKS.json` 汇总状态 | B 或被用户明确指定的调度者 | A/C/D 交自己的报告，不同时覆盖总表 |

任务输出中分配给 A/B 的专属证据文件（包括 `qa/evidence/Axx.md`、`qa/evidence/Bxx.md` 和 B01 生成记录）可由对应开发写；D 维护独立 QA 结果和总索引。费用台账由 B 唯一初始化和维护；D 只读后写独立 `docs/ops/budget-review.md`。已有仓库约定优先，S01 记录这些细节。

统一使用 [LiliLIN0324/scendance](https://github.com/LiliLIN0324/scendance)。每人独立 clone；每项任务从最新 `main` 建短分支，例如 `codex/a-a08-floorplan`、`codex/b-b08-public-assets`、`codex/c-c02-fixtures`、`codex/d-d02-checklist`。通过 PR 合并，不共用一个工作目录或四条长期开发分支。A 的代码由 B 评审；B 的代码由 A 评审；C 的数据由使用它的 A/B 校验，D 的验收和讲稿由 C 核实产品表述。B 负责集成，不能用自审代替其他成员检查。具体操作见 GITHUB.md。

GitHub Issue 用于领取任务、讨论依赖和记录阻塞，PR 用于交付；TASKS.json 是唯一状态真源，仍由 B 汇总。Issue 或 PR 创建不代表任务完成。合并前检查变更和实际证据；PR 已合并但真实验收未通过时，任务保持 review/blocked。

新增文件边界：A 维护平面图标定/描边和公共模型预览加入界面；B 维护图纸私有存储、轮廓校验、公共库适配和资产归档；C 维护图纸样例、素材来源/授权与布局数据；D 维护这些流程的真实验收。实际代码目录在 S01 冻结。

## 2. 任务调度与交接

1. 每人先读总说明、自己的提示词、任务卡和共享契约。
2. 每人同时最多一个主要任务；选 `todo` 且 `depends_on` 全部 `done` 的任务。无就绪任务时继续已明确的准备工作，或报告阻塞，不抢改其他人的模块。
3. `complete_after` 允许前端在后端未完成时依模拟响应实现，也允许 G0/C06 先收集失败报告和开展评审。G0 不需等所有验证通过才启动；C06 不需等 D04 通过才讨论范围。标 `done` 前，所有完成依赖与验收仍必须通过；范围改变要先有明确决定并同步任务表。
4. 状态流为 `todo → in_progress → review → done`。缺少必要环境或输入时标 `blocked`，填阻塞人、所需信息及仍可做的工作。
5. A/B 每次交付至少带接口版本、实际运行入口、成功和失败样例；C 交可加载数据；D 交复现步骤与证据。
6. D 发现问题后，A/B 直接进入自己模块的修复循环，不等待最终测试任务完成。修复造成旧证据失效时回退相关任务状态并重新验证。
7. 保持原始 PLAN 不变。删改必做范围需 C 记录决策和人类团队的明确决定，联动更新任务、验收和路演；不能悄悄将失败功能删除后宣布全部完成。

## 3. 阶段出口

| 相对时间 | 必须拿到的东西 | 牵头 |
|---|---|---|
| 0–4 小时 | 底座、真实账号、生成和公共库可行性有证据；契约包含图纸/多边形/公共模型；核对大陆网络 | A/B 实现，D 实测，C 记录 G0 |
| 4–16 小时 | 八类物料、平面图标定/轮廓样例；两账号保存和交接；公共库接入与完整测试清单推进 | A/B，C 提内容，D 执行早期测试 |
| 16–28 小时 | 平面图/轮廓与公共模型保存重开；AI 提案、真实生成归档和加入；失败与冲突明确 | A/B，C 检查内容，D 复验 |
| 28–36 小时 | 冻结快照、物料表、手机查看与分享撤销；完整演示项目 | A/B/C，D 更新 PPT 和脚本 |
| 36–44 小时 | 必做验收、类型/构建/相关测试通过；无未解决 P0/P1 | D 验证，A/B 修复，C 验收 |
| 44–48 小时 | 冻结版本、真实演示录像、备份、恢复与计时排练 | D 主讲，C 操作，A/B 保障 |

这些时间是计划窗口，不是依赖已解决的保证，也不是要求连续工作 48 小时。最新 PLAN 新增平面图、多边形和公共模型，原排期没有单列投入；G0 必须重估，不通过删除新增必做项来维持表面准时。前四小时失败时及时记录并重排。

## 4. 问题优先级

- P0：流程无法继续、数据丢失、越权读写、付费重复提交等阻断问题；先修复。
- P1：计划必做行为不符，包括手机查看、陈旧提案或物料表错误；最终原范围验收前解决。
- P2：不影响任务完成的视觉或文字细节；由 C 决定修复顺序。

报告只写实际观察和可验证原因。问题记录最少包含：版本、设备、账号角色、前置数据、步骤、预期、实际、截图/日志、负责人、复验结果。对待验证的原因标“推测”。

## 5. 实测和操作边界

- 每个完成结论都附证据；没执行写 `not_run`，环境限制写 `blocked`，失败写 `fail`。
- 本地或模拟结果不能替代真实云保存、真实生成、真实权限和真实手机验收。
- 密钥由成员在安全环境配置；报告只含变量名和是否验证，不含秘密值。
- 本包不指示 AI 注册/购买/充值/联系第三方；需要时由该任务的人类负责人处理。已有授权范围内的实现、读操作和可逆本地工作正常推进。
- 技术栈、模型名和第三方接口沿用原计划作为候选，B01/S01 按当前官方资料与实际账号核实；不能将计划中的调研结论视为已成功接入。
